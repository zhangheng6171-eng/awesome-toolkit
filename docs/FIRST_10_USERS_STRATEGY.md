# 前 10 个用户反馈策略

> 目标：用前 10 个真实用户的反馈，科学决定下一步开发优先级。
> 原则：不猜测用户想要什么，让他们告诉你。

---

## 一、反馈收集框架

### 每个用户反馈映射到 3 个维度

| 维度 | 含义 | 测量方式 |
|------|------|----------|
| **F (Frequency)** | 多少人遇到？ | N/10 用户提到相同问题 |
| **I (Impact)** | 对体验影响多大？ | 1=不影响使用 5=完全阻塞 |
| **E (Effort)** | 修复需要多少时间？ | 1=几分钟 5=数周 |

### 优先级公式

```
Priority Score = F × 2 + I × 3 - E × 1
```

- F（频率）权重 2：多人提到的问题优先
- I（影响）权重 3：严重阻塞的问题最优先
- E（成本）权重 -1：低成本修复可以快速验证

---

## 二、反馈分类矩阵

### 按用户类型分类

不同背景的用户遇到的困难不同，需要分类分析：

| 用户类型 | 关键问题 | 如果这类用户反馈最多 |
|----------|----------|---------------------|
| **无服务器 / 无技术背景** | "Agent 是什么？""Token 在哪找？""SSH 是什么？" | 优先做新手引导和术语解释 |
| **有服务器 / 无 Docker 经验** | 部署向导连接失败、不知道如何安装 Agent | 优先优化 Agent 安装流程 |
| **有 Docker 经验** | 想自定义配置、需要更多部署选项 | 优先开放 compose 文件自定义 |
| **纯浏览用户** | 搜索不好用、工具信息不全 | 优先优化搜索和内容质量 |

### 按反馈情绪分类

| 情绪 | 信号 | 行动 |
|------|------|------|
| 😤 沮丧 / 困惑 | 用户想用但不知道怎么做 | 修复教程和引导 |
| 😕 失望 | 用户预期和实际不符 | 调整首页传达的价值主张 |
| 😐 中性 | 没特别感觉 | 找差异化的机会 |
| 😊 满意 | 功能达到了预期 | 保持，作为参考标准 |
| 🤩 惊喜 | 超出预期 | **放大这个功能** — 这是增长的机会 |

## 三、决策流程

### 收到第 1-3 个反馈时

**不要急于改代码。** 先做：

1. **确认问题类型：**
   - Bug（代码有问题）→ 直接修复
   - UX 问题（代码没问题，但用户不会用）→ 观察是否重复出现
   - Feature Request（新功能需求）→ 记下来，不着急实现

2. **问追问：**
   - "你当时想做什么？"（了解上下文）
   - "你期望的结果是什么？"（了解预期）
   - "如果换个方式实现，你会接受吗？"（探索替代方案）

3. **先修复 P0 Bug + 容易修复的 P1：**
   - Cloudflare Access 配置（阻塞 Dashboard）
   - OG 图片（阻塞社交分享）
   - 明显的文案错误

### 收到第 4-7 个反馈时

**开始识别模式：**

1. **计算频率：**
   - ≥ 3 人提到的问题 → 高优先级
   - 1-2 人提到的问题 → 继续观察
   - 0 人提到（你担心的） → 可能不是问题

2. **识别「致命缺陷」：**
   - 如果 ≥ 3 个用户在同一个地方放弃 → 立即修复
   - 如果 ≥ 2 个用户说"我不会再用了" → 了解原因，优先处理

3. **寻找「惊喜时刻」：**
   - 哪 1-2 个功能被用户自发提到"好用"？
   - 放大这些功能，让更多用户能体验到

### 收到第 8-10 个反馈时

**做一次完整的优先级排序：**

1. **关闭反馈收集窗口**（至少关闭一段时间）
2. **把所有问题列在一张表里**
3. **用 Priority Score 排序**
4. **选 TOP 5 修复**

## 四、10 个用户后的决策框架

### 场景 A：大多数用户「浏览但不部署」

**信号：** 7+/10 用户只是逛了逛，没有尝试部署。

**可能原因：**
- 没有服务器（最常见）
- 部署流程太复杂
- 不信任 Agent

**行动：**
1. 降低部署门槛（提供免费试用服务器链接、Sandbox 环境）
2. 首页增加「成功案例」和「部署过程预览视频」
3. 增加「本地试用」（无需服务器的体验模式）
4. 优先做内容质量（AI 描述生成、更多工具、对比功能）

**KPI：** 浏览 → 点击「一键部署」的转化率

---

### 场景 B：用户尝试部署但失败

**信号：** 5+/10 用户进入部署向导但没完成。

**最可能的卡点：**
1. Agent 安装步骤（用户不知道如何 SSH）
2. 连接测试失败（防火墙 / Token 问题）
3. 部署执行报错（docker-compose.yml 有问题）

**行动：**
1. 优先修复 Agent 安装和连接流程
2. 增加「连接失败排查指南」
3. 在真实 VPS 上测试全部 32 个部署配置
4. 增加 WebSocket/SSE 稳定性

**KPI：** 部署向导完成率

---

### 场景 C：用户部署成功但体验差

**信号：** 部署成功了，但用户反馈"不知道怎么用""不知道部署完去哪看"。

**行动：**
1. 增加「部署后指南」（怎么访问、怎么配置、初始密码）
2. Dashboard 增加部署后状态（运行中 / 已停止 / 需要更新）
3. 增加工具使用文档链接

**KPI：** 部署后工具的 7 天留存率

---

### 场景 D：用户很喜欢但想要更多

**信号：** 正面反馈为主，主要问题是"支持的工具太少"。

**行动：**
1. 优先扩充工具库和部署配置
2. 开放用户提交部署配置的通道
3. 接入支付（Pro 版需求验证了）

**KPI：** 用户推荐率（NPS）

---

## 五、不应过早做的事情

即使前 10 个用户反馈了，以下事项也不要在第一个迭代做：

| 不要做的事 | 原因 | 什么时候做 |
|------------|------|------------|
| 接入支付 | 前 10 个用户不足以验证付费意愿 | 50+ 活跃用户后 |
| 用户系统 / 注册登录 | 增加复杂度，当前 Cloudflare Access 够用 | 100+ 用户或支付前 |
| 国际化 / 英文版 | 中文用户还没验证 | 中文市场站稳后 |
| 大规模重构 | 在验证需求前不应重写 | 确认产品方向后 |
| 增加复杂功能（监控/告警/自动备份） | 先验证核心「浏览→部署」流程 | 核心流程优化后 |

## 六、第一个迭代的推荐计划

### Week 1（基于前 5 个用户反馈）

| 优先做 | 为什么 |
|--------|--------|
| 修复所有 P0/P1 Bug | 阻塞用户体验 |
| 部署向导新手引导优化 | 这是核心转化路径 |
| Agent 安装文档补充（配图/Screencast） | 降低部署门槛 |
| 搜索增加拼音支持 | 中文用户基础体验 |

### Week 2（基于 6-10 个用户反馈）

| 优先做 | 为什么 |
|--------|--------|
| 反馈中 ≥ 3 人提到的问题 | 已确认的模式 |
| 移动端体验优化 | 很多中国用户只用手机 |
| 增加「部署后指南」 | 提高完成率 |
| AI 描述生成（丰富工具内容） | 提升浏览体验 |

### Week 3+（10+ 用户后）

| 优先做 | 条件 |
|--------|------|
| 工具库扩充到 80-100 个 | 如果用户主要需求是「更多工具」 |
| 支付接入 | 如果 ≥ 3 人自发表示「愿意付费」 |
| Agent 增强（备份/更新通知） | 如果部署成功率 ≥ 70% |
| 社区功能（用户提交部署配置） | 如果用户主动问「怎么贡献」 |

## 七、度量指标

前 10 个用户期间，只跟踪这 5 个指标：

| 指标 | 当前基线 | 目标 |
|------|----------|------|
| 部署向导完成率 | ?% | ≥ 50% |
| 部署成功率（Agent 连接 + compose up） | ?% | ≥ 70% |
| 首页 → 工具详情点击率 | ?% | ≥ 60% |
| 用户反馈率（反馈 / 访问） | ?% | ≥ 10% |
| 7 天回访率 | ?% | ≥ 20% |

> 所有基线标注为 "?" 的指标都需要在 10 个用户测试后获得第一个数据点。
